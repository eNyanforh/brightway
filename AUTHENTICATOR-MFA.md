# BrightWay Sprint 1 — authenticator app and backup codes

## Scope

User choices: time-based authenticator-app codes with backup codes; enrollment optional for individuals and required for Admin/reviewer actions. This package implements that policy for the current credential-review Admin workspace, including reviewer evidence reads. It does not create a Super Admin dashboard, school accounts, organization onboarding or context switching. The organization-routing package remains on hold.

This ZIP is a cumulative source update for the existing BrightWay project. It includes the earlier Sprint 1 credential workspace and password-recovery files, with the registered-recipient correction. Preserve your other project files, backend/.env and all previously applied migrations. Do not apply it over an already migrated organization-routing version without reconciling that version first.

## 1. Generate the server encryption key

Run this on your own computer:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Copy the resulting 64 hexadecimal characters into backend/.env:

```dotenv
MFA_ENCRYPTION_KEY="paste-your-generated-64-hexadecimal-characters-here"
```

Use your generated value, not the placeholder above. Keep this key separate from EMAIL_VERIFICATION_SECRET. Keep a secure copy with your server configuration backups; existing authenticator secrets need it to decrypt. Do not put the actual key in .env.example, frontend configuration, Git or chat. Changing it casually breaks existing app-code verification; automated encryption-key rotation is not included.

The existing Resend settings still serve signup and password recovery. Authenticator login itself sends no email or SMS and adds no new package dependencies.

## 3. Enable two-factor authentication

1. Log in normally. On Profile, select Account security, or open /security.
2. Enter your current password and select Set up authenticator.
3. In an authenticator app supporting TOTP, add an account using a setup key. This increment uses manual key entry rather than a QR code. Enter the shown account label and secret; use time-based codes, SHA-1, 6 digits and a 30-second period. Use automatic time on your device.
4. Enter a current code generated by the app and select Enable two-factor authentication. Setup expires after ten minutes. Merely starting setup does not enable 2FA.
5. Save the ten backup codes using Download backup codes or your own secure method. They are displayed only in this response. Each works once. Keep them private and separate from the authenticator.
6. Select I saved my codes. Your current session has proved 2FA; other sessions are signed out. You can use authorized reviewer tools immediately if your account already has the required reviewer role.

Enabling 2FA does not grant an Admin role, individual Verified status or credential approval. Reviewer role assignment remains a trusted server operation; the limited credential-review role is not a complete Super Admin role.

## 4. Login and recovery

- Unenrolled individuals keep password-only login. Enrolled users must complete the authenticator/backup-code step on every new login.
- A valid password creates only a five-minute pre-login challenge, held in a separate HttpOnly cookie. It cannot authenticate a protected API. No full session cookie or account JSON is issued at this stage.
- Enter a fresh app code or one unused backup code. Successful verification creates the normal session and consumes that challenge. The raw session/challenge token is never returned in JSON.
- App codes have a 30-second time step, allowing one adjacent step of clock drift. An already accepted counter cannot be reused for login or configuration changes. Wait for a new app code if the current one was just used during setup or another action.
- There are five attempts per login challenge. A persistent per-account budget also blocks checks after five failed attempts within five minutes, even if another password login creates a new challenge. Wait five minutes and sign in again after exhausting attempts.
- The most recent password login replaces the earlier pending challenge for that account. Use another account cancels the pending challenge. Logout clears/revokes pending challenges as well as ordinary sessions.
- Password reset changes the password and revokes existing sessions. It does not disable 2FA, replace its secret, replenish backup codes, or grant a full login session. Pending MFA challenges are also bound to the password hash that was checked before issuance, so they cannot survive a password change.

### Lost authenticator

Use an unused backup code after your password to log in. Open Account security to generate new backup codes or replace the authenticator. Regenerating codes requires your current password and either a fresh app/backup code, or a session that proved 2FA within the last five minutes. This recent-session path lets someone using their last backup code recover and lets a user retry if a regeneration response was lost. Password-only regeneration does not extend the original five-minute assurance window.

To replace a lost authenticator: first save replacement backup codes, then disable the old factor using your current password plus one unused backup code, and enroll a new authenticator. Disabling always requires a fresh proof. Reviewer actions are blocked while the factor is disabled.

If both the authenticator and every backup code are lost, there is no automatic email-based MFA bypass in this increment. An independently verified support-recovery policy/workflow is still needed; do not edit database flags or grant fake verification to work around this. Audited backup-code recovery is included; loss of all factors is not.

## 5. Access and data protections

- Authenticator secrets use AES-256-GCM with a fresh nonce and account-bound associated data. Only setup returns the new manual secret; status responses never reveal stored secrets or backup-code hashes.
- Backup codes contain 96 bits of random entropy and are stored only as hashes. Generated plaintext codes remain in component memory until dismissed/unmounted or deliberately downloaded by the owner; they are not stored in localStorage/sessionStorage or URLs.
- Setup requires the existing password. Enabling requires a valid code and the still-valid authenticated setup session. Disabling or regenerating backups rechecks the password and second-factor/session assurance.
- Factor changes increment its version, revoke other sessions and invalidate pending login challenges. Every session read binds to the factor's current version. A stale cookie cannot retain its old second-factor assurance after enrollment, regeneration, disable or reset. The current session is deliberately retained at its appropriate assurance level; other sessions are revoked.
- The existing /admin/credentials routes require a server-confirmed 2FA session in addition to existing reviewer role/active-account/email/self-review rules. Changing browser flags cannot grant this. Role elevation does not bypass 2FA.
- A reviewer downloading another person's evidence needs the same assurance and assignment checks. An owner can still download their own supporting evidence without enrolling.
- Assignment/decision writes recheck the current 2FA session inside the credential transaction after locking the reviewer account, so a revoked session cannot win a later review decision.
- Future privileged routes must use the same server-side requirement; this package does not claim to protect future dashboards that do not exist yet.
- Audit records capture account, action, time and proof method for enrollment, enabling, disabling, backup regeneration and successful second-factor login. Passwords, secrets, app codes and plaintext backup codes are not audit fields.
- Login and MFA endpoints enforce trusted Origin on mutations, private no-store responses, strict input allowlists and per-process IP limits. Password login now counts all requests toward 20 per 15 minutes, including successful password steps. MFA routes share 30 requests per 15 minutes per IP. Production with multiple backend instances should also have shared ingress limits.

## 7. Browser acceptance

1. Before enrollment, confirm an ordinary account can log in without an extra code. A reviewer without enrollment must be blocked from its reviewer workspace and other-owner evidence reads.
2. Follow setup using a real authenticator. Confirm a wrong setup code does not enable 2FA. Save the resulting backup codes privately.
3. Confirm other existing sessions are signed out. Log out, then log in: the password step must remain outside protected pages until a valid app code is provided. Try accessing protected API routes with only the pending challenge cookie; they must reject access.
4. Use a backup code to log in; try replaying it in a new challenge. Only the first successful use should work. Confirm the unused count decreases.
5. Regenerate backups and confirm all old backups fail. Test the last-code recovery/password-confirmed five-minute path. After five minutes, regenerating without a fresh code must fail; retries must not extend this window.
6. Start login, select Use another account, and confirm its pending challenge cannot finish. Check wrong-code retry, challenge expiry and five-failure cooldown behavior.
7. Reset the password through the existing email recovery flow. Confirm the new password still requires 2FA, old sessions fail and old pending challenges cannot finish.
8. As an enrolled authorized reviewer, assign a different user's claim and make a decision. Disable 2FA in another session or revoke the relevant session, then verify stale review/evidence requests fail. Owners must retain their private evidence access.
9. Check labels, keyboard navigation, code focus after password submission, error preservation, backup-code dismissal and narrow mobile layout. Do not paste backup codes, secrets or actual encryption keys into bug reports.

This removes expired login challenges and clears expired, never-enabled setup secrets. It does not remove enabled factors or audit history. Schedule it when deployment operations are addressed; no schedule/deployment is created here.
